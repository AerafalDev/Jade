# ADR-0014: Dear ImGui, its extensions and backends

- Status: Proposed
- Date: 2026-10-03

## Context

The user wants Dear ImGui "with all its extensions" in Jade. Everything bundled goes into
`jade_native` ([ADR-0003](0003-single-combined-native-library.md)) and is bound by our generator
([ADR-0005](0005-in-house-binding-generator.md), [ADR-0006](0006-binding-api-shape.md)), so each
library needs an exported C API. Dear ImGui and every extension are C++. Task 301 surveyed the
candidates; this ADR records the result.

Facts checked on 2026-10-03 (sources at the end, measurements from task 301's throwaway builds,
whose commands are in the 301 Outcome):

- Dear ImGui `v1.92.9b` (2026-07-31) is the latest release. Every 1.92.x release has a matching
  `-docking` tag; `v1.92.9b-docking` is commit `b48d1afbe8ee`. MIT.
- dear_bindings (MIT) lives in the `dearimgui` GitHub organisation, whose public member is ImGui's
  author. Its `v0.24` (2026-09-27) publishes, for each ImGui release and for master and docking,
  `dcimgui.{h,cpp,json}`, `dcimgui_internal.*` and C wrappers of the backends, including
  `dcimgui_impl_sdl3`, `dcimgui_impl_wgpu` and `dcimgui_impl_null`. It only converts ImGui's own
  headers: on extension headers it fails (it needs a per-header template, and namespace flattening
  is hard-wired to `ImGui::`), and ImPlot's templates are an open issue (#78, open since 2024-09).
- cimgui (MIT) and its family of wrappers (cimplot, cimplot3d, cimguizmo, cimnodes, cimnodes_editor,
  cimCTE) are generated by one Lua generator and pin each extension through a git submodule. cimgui,
  cimplot and cimguizmo carry an MIT license; cimplot3d, cimnodes, cimnodes_editor and cimCTE have no
  license file. ImGui.NET and Hexa.NET.ImGui both build on cimgui.
- dcimgui keeps ImGui's comments (3,245 comment lines in the released `dcimgui.h`, comments on 555
  of its 790 functions in `dcimgui.json`); `cimgui.h` has 13 comment lines and its
  `definitions.json` none.
- The upstream backends `imgui_impl_sdl3.cpp` (1,317 lines) and `imgui_impl_wgpu.cpp` (1,162 lines)
  received 19 and 49 commits on the docking branch in the last 12 months. Both compile without
  warnings (`-Wall -Wextra`) against the SDL 3.4.16 and Dawn `v20260930.214659` headers that
  `jade_native` stages, and with Emscripten 6.0.11 using `--use-port=emdawnwebgpu`.

## Decision

### 1. Branch and version

- Dear ImGui's **docking** branch, pinned to a docking release tag: `v1.92.9b-docking` today.
  Docking and multi-viewports are what an editor needs, every 1.92.x release ships a docking tag, and
  both dear_bindings and cimgui publish docking outputs.
- ImGui is compiled with `IMGUI_DISABLE_OBSOLETE_FUNCTIONS`. Deprecated API stays out of the public
  bindings, and the cimgui headers that some extensions use assume it (their struct layouts match
  dcimgui's only with it). Every selected extension compiles with it at the revisions below.
- One ImGui version for everything. A bump moves ImGui, the dear_bindings release for that version
  and every extension together, and is checked by compiling each extension against it.

### 2. C API of Dear ImGui and its backends: dear_bindings

- The C API is dear_bindings' prebuilt release for the pinned tag
  (`DearBindings_v0.24_ImGui_v1.92.9b-docking.zip`), downloaded and checked by SHA-256 like any other
  upstream. No Python runs at build time.
- Bound and exported: `dcimgui` (790 functions) and the `sdl3`, `wgpu` and `null` backend wrappers
  (13, 16 and 10 functions). `dcimgui_internal` (829 functions, including the DockBuilder API) is a
  later, separate step: dear_bindings calls it semi-experimental and ImGui does not keep it stable.
- Chosen over cimgui for the core because it preserves the comments the XML docs need (ADR-0006),
  its metadata is richer (references, non-nullable pointers, field defaults, default-argument helpers,
  original C++ names, preprocessor conditionals), its release already contains the WebGPU backend
  (cimgui's committed backend output covers GLFW, OpenGL 2/3, SDL2, SDL3 and Vulkan), and it lives in
  ImGui's own GitHub organisation.

### 3. Generator input: libclang over the dcimgui headers, `dcimgui.json` as annotations

- The declarations come from libclang over `dcimgui.h` and the backend headers, through the existing
  C reader. This keeps the per-triple parse and the layout check of ADR-0005. The headers parse with
  0 errors for all 12 ADR-0007 triples once the generator's stub sysroot gains an `assert.h` (the WGPU
  backend header needs emdawnwebgpu's headers on browser-wasm).
- `dcimgui.json` is read by the ImGui library configuration as an annotation source, not as a second
  model reader: `is_reference` drives `ref`/`in`/`out` overloads, `original_fully_qualified_name` and
  `is_default_argument_helper` give C# names and overloads, field `default_value` gives defaults for
  structs that C++ constructors used to initialise (`ImFontConfig`, `ImGui_ImplWGPU_InitInfo`), and
  `conditionals` are checked against the build defines. The JSON has no per-target sizes or offsets,
  so it cannot replace libclang.
- The varargs functions (15) are excluded; the `*Unformatted` helpers the release contains (13) are
  bound instead.

### 4. Backends: upstream C++ compiled into `jade_native`

- `imgui_impl_sdl3.cpp`, `imgui_impl_wgpu.cpp` (with `IMGUI_IMPL_WEBGPU_BACKEND_DAWN`) and
  `imgui_impl_null.cpp`, plus their dear_bindings wrappers, are compiled into `jade_native` and bound
  like the core. They are not ported to C#.
- Reasons: they are ImGui's reference implementations and follow every Dawn, emdawnwebgpu and SDL
  change (49 and 19 commits a year); a port would have to replay each one. Rendering one frame costs
  one P/Invoke (`RenderDrawData`) instead of every WebGPU call crossing the boundary, which matters
  most in the browser. Mobile and web behaviour is handled upstream: touch reported as a mouse source,
  text input through `SDL_StartTextInput`, and platform windows only on the `windows`, `cocoa` and
  `x11` SDL drivers.
- The null backend gives headless tests a platform and a renderer.
- The engine can still render `ImDrawData` in C# inside its own render graph later; the bindings
  expose everything it needs. That is an engine-phase choice, not part of the interop layer.

### 5. Extensions

the extension's C++ API exported) over ImGui core plus dcimgui (1,245 KiB), measured at each
project's default-branch head of 2026-10-03. `jade_native` hides C++ symbols, so they are upper
bounds. "Compiles" means: the revision given compiles against `v1.92.9b-docking` on linux-x64 with
and without `IMGUI_DISABLE_OBSOLETE_FUNCTIONS`, and the default-branch heads also compile for
browser-wasm (Emscripten 6.0.11), x86_64-windows-gnu and aarch64-macos (zig 0.16 as a cross-compiler,

### 6. How an extension gets its C API, in order of preference

1. An upstream-maintained C API compiled from the pinned sources (imspinner's `cimspinner/`,
   ImGuiFileDialog's `IGFD_*`).
2. A cimgui-family wrapper **with a license**, compiled from its pinned commit, with the extension
   pinned to the wrapper's own submodule commit (the wrapper is generated from that exact header). It
   compiles against `cimgui.h` from the cimgui commit generated for the same ImGui tag (`125f397e`
   for `v1.92.9b-docking`); `cimgui.cpp` is not linked (checked: no undefined symbol beyond the
   extension's own demo files). The generator maps the ImGui types these headers use (`ImVec2`,
   `ImDrawList`, ...) to the ImGui bindings by C name and checks that both headers give them the same
   layout (they do on x86_64 Linux, arm64 Windows and wasm32 for all 69 public structs, with
   `IMGUI_DISABLE_OBSOLETE_FUNCTIONS`).
3. Otherwise a hand-written `jade_imgui_<ext>_*` C shim in `native/shims/`, using dcimgui's C types
   and the `namespace cimgui { #include "dcimgui.h" }` pattern of `dcimgui.cpp`.

ImPlot3D and imnodes move to route 2 if their wrappers get a license; otherwise imnodes takes route
3 and ImPlot3D waits. If more template-heavy C++ libraries need C APIs, revisit the alternative of a
C++ reader in our own generator (below).

## Alternatives considered

- **master branch**: smaller, but no docking. The docking tags cost nothing extra to track.
- **cimgui for everything**: one generator and one type universe for core and extensions, prior art
  in ImGui.NET and Hexa.NET.ImGui. Rejected for the core because its output has no comments (no XML
  docs), its backend output lacks WebGPU, and four of its six extension wrappers are unlicensed
  anyway.
- **dear_bindings JSON as the only generator input**: it carries no per-target layout, so libclang is
  still needed for ADR-0005's variance check; two readers would then describe the same declarations.
- **C# ports of the backends**: full control and C# debugging, but every upstream fix has to be ported
  by hand, each WebGPU call becomes a P/Invoke, and the web and mobile quirks handled upstream would
  have to be rediscovered.
- **A C++ reader in our generator** that emits the `extern "C"` shim and the C# from one model
  (dear_bindings' approach in C#, over libclang): uniform docs and naming for every extension and no
  dependency on unlicensed wrappers, but a feature as large as the 201 generator core (overloads,
  references, by-value class conversion, templates, `std::string`). Not justified for the two
  extensions that only lack a license today; it becomes the fallback if the license requests fail.
- **ImPlot with only `float` and `double`**: four times smaller, but cimplot's published wrapper
  instantiates all ten types, so restricting them means regenerating cimplot with its Lua generator.
  Kept at ten types until browser-wasm download size says otherwise.

## Consequences

- `jade_native` grows by about 1.5 MB (core and demo; the two backends add about 32 KB of code) plus
  about 8 MB with every selected extension on linux-x64, nearly three quarters of it ImPlot. The
  staged linux-x64 `libjade_native.so` (Dawn, SDL3, miniaudio) was 11.9 MB on 2026-10-03. Native code
  compresses well (ImPlot's growth is about 0.9 MB with gzip -9), so the 250 MB nuget.org limit is
  not at risk.
- With the WGPU renderer, docking works but multi-viewports do not: the upstream WebGPU backend lacks
  multi-viewport support.
- On macOS, `imgui_impl_wgpu.cpp` must be compiled as Objective-C++ (its surface helper includes
  Cocoa).
- C++ default member initialisers are lost in C (`ImGui_ImplWGPU_InitInfo` needs
  `NumFramesInFlight = 3` and a multisample state with `count = 1`, `mask = 0xFFFFFFFF`). The JSON
  defaults let the generator restore them.
- On browser-wasm the WebGPU backend requires Emscripten 4.0.10 or later with emdawnwebgpu, the same
  constraint task 105 already faces for Dawn.
- The generator needs new features before ImGui can be bound: bit-fields, anonymous members, fixed
  arrays of structs, callback typedefs, types shared with other libraries (SDL3, WebGPU, ImGui), and
  JSON annotations.
- The unlicensed wrappers are a dependency on someone else's action: ask their author to add a
  license before relying on them.
