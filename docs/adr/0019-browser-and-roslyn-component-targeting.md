# 0019. Targeting of the browser interop project and the Roslyn components

- Status: Accepted
- Date: 2026-10-05

## Context

[0003](0003-csharp-15-and-dotnet-11.md) left the target framework and runtime identifier of
browser-specific projects to be settled when they are created, and states both that the whole
repository uses C# 15 and that `LangVersion` is left to the TFM default. Creating the projects
showed that these points need an explicit rule.

Verified on 2026-10-05 with SDK `11.0.100-rc.1.26425.128` and its `wasm-tools` workload:

- `net11.0-browser` is a valid TFM: the `microsoft.net.workload.mono.toolchain.current` manifest
  declares the `browser` target platform (version 1.0), and a `net11.0-browser` library builds with
  `[assembly: SupportedOSPlatform("browser1.0")]` generated by the SDK.
- The `wasmbrowser` template creates a `Microsoft.NET.Sdk.WebAssembly` project with
  `TargetFramework` `net11.0`; the SDK sets `RuntimeIdentifier` to `browser-wasm` and leaves
  `TargetPlatformIdentifier` empty.
- A `net11.0` project cannot reference a `net11.0-browser` project: restore fails with NU1201, and
  `dotnet add reference` refuses it for the template's browser application.
- For `netstandard2.0` the default `LangVersion` is 7.3, and `Nullable` `enable` then fails with
  CS8630.
- The SDK's compiler is Roslyn `5.11.0-1.26425.128`; the latest stable
  `Microsoft.CodeAnalysis.CSharp` on nuget.org is 5.9.0.

## Decision

- `Jade.Emscripten` targets `net11.0`, without a runtime identifier, like every managed library
  ([0012](0012-supported-targets.md)). Its `Properties/AssemblyInfo.cs` declares
  `[assembly: SupportedOSPlatform("browser")]`, so CA1416 requires callers to guard its APIs with
  `OperatingSystem.IsBrowser()` ([0016](0016-public-api-conventions.md)).
- `Jade` references `Jade.Emscripten` unconditionally; browser applications target `net11.0` with
  the `browser-wasm` runtime identifier, as the SDK template does.
- The Roslyn components (`netstandard2.0`) set `LangVersion` to `15.0` explicitly. Every other
  project keeps the TFM default. Preview language versions stay forbidden.
- The Roslyn components reference a `Microsoft.CodeAnalysis.CSharp` version no newer than the
  compiler of the SDK pinned in `global.json`, since an analyzer built against a newer Roslyn fails
  to load in an older compiler.

## Consequences

- Engine code compiles once for every platform; browser-only paths are visible through CA1416
  instead of separate target frameworks.
- `Jade.Emscripten` ships to every platform even though it is only usable in the browser; it
  contains declarations only, which the trimmer removes from other targets.
- C# 15 language features that need runtime or library support (for example `init` or `required`
  members) need polyfills in the Roslyn components.
- Raising `Microsoft.CodeAnalysis.CSharp` is tied to SDK updates and must be checked against the
  compiler version of the pinned SDK.

## Alternatives considered

- **`net11.0-browser` for `Jade.Emscripten`.** The SDK generates the platform attribute, but neither
  `Jade` nor a standard browser application (`net11.0`) could reference it; `Jade` would have to
  multi-target and applications would have to change their TFM.
- **`net11.0` with `RuntimeIdentifier` `browser-wasm` in the library.** Managed code would become
  RID-specific, against [0012](0012-supported-targets.md), for no benefit: the native linking
  happens when the application is built.
- **TFM default `LangVersion` for the Roslyn components.** C# 7.3 cannot use nullable reference
  types, which `Directory.Build.props` enables everywhere.
