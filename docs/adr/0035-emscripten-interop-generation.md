# 0035. Emscripten interop generated from its C headers

- Status: Accepted
- Date: 2026-10-05

## Context

`Jade.Emscripten` is the browser-only interop project ([0019](0019-browser-and-roslyn-component-targeting.md));
the browser sample (roadmap task 15) needs from it a `requestAnimationFrame` loop, the canvas size,
the device pixel ratio and some HTML5 events. Emscripten exposes them as a C API
(`emscripten/emscripten.h`, `emscripten/html5.h`). [0007](0007-in-house-binding-generator.md) and
[0026](0026-binding-generator-pipeline.md) only cover Dawn, SDL3 and miniaudio, and nothing said
whether this interop is generated or written by hand.

Known on 2026-10-05:

- The C header front-end of [0033](0033-c-header-raw-layer-generation.md) parses, merges, annotates
  and emits any C API; it needs no new parsing code for Emscripten's headers.
- The Emscripten of the SDK's `wasm-tools` workload is built from the `dotnet/emscripten` fork and
  equals no upstream release ([0025](0025-browser-natives-with-workload-emscripten.md)); it is not
  a dependency of `build/versions.json` pinned to a GitHub commit like the others.
- Not verified: the name under which `LibraryImport` resolves Emscripten functions linked
  statically into the application's native module, and how callbacks marked
  `[UnmanagedCallersOnly]` behave under Mono WebAssembly.

## Decision

- `Jade.Emscripten`'s raw layer is generated by the binding generator from Emscripten's C headers,
  through the C header front-end and the names of [0034](0034-raw-layer-with-dotnet-names.md),
  with a `bindings.json` like the other interop projects. The maintainer chose this over a
  hand-written surface.
- The task that does it settles, each with its verification:
  - where the headers come from: the `dotnet/emscripten` fork at the commit that the SDK's VMR
    pins, fetched like the other sources, or the installed workload pack, which would make the CI
    jobs that regenerate install the workload;
  - the targets of a library: Emscripten is parsed for `browser-wasm` only, and its declarations
    carry no per-member platform attribute, since the assembly is browser-only;
  - the import name of statically linked functions, and the callbacks.

## Consequences

- The browser interop follows the same pipeline, regeneration check and naming as the others.
- The generator gains per-library targets and, depending on the choice above, a new kind of pinned
  source; `build/versions.json` or the toolchain check of the native CI follows it.
- Until that task, `Jade.Emscripten` stays empty.

## Alternatives considered

- **A hand-written surface**: about ten `LibraryImport` declarations and `[JSImport]` for what lives
  in JavaScript; less machinery for a small surface, but a second way of writing interop.
